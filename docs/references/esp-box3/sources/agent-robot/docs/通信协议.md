# 第三方终端接入协议：Device Protocol 1.0

本文面向第三方硬件终端、桌面终端和软件终端的开发者，说明如何通过 ez-assistant Runtime Host
的 Device Gateway 接入 Agent。终端可以自行选择芯片、操作系统、网络配置方式和交互界面。

核对日期：2026-10-20。Wire 版本为 `protocol_major=1`、`protocol_minor=0`。本文是现有协议的
接入说明，不引入新的消息或兼容层，也不将当前 ESP32 的 GPIO、PTT 或 Wi-Fi NVS 布局变成协议要求。
普通用户的配置与配对操作见[操作说明](操作说明.md)。

## 1. 接入边界与实现顺序

```text
第三方终端 ── mDNS / TLS / WebSocket ── Device Gateway
                                             ├── ASR / TTS
                                             └── 当前主控代理会话 → Agent Runtime
```

- 终端主动连接 Host，不需要向局域网开放服务端口。
- Agent、模型、业务会话和权威输入状态由 Runtime 持有。终端处理交互、收音、播放和显示。
- 设备协议不使用 Desktop 的 Bearer Token，不调用 Desktop Command/SSE 接口，不直连模型。
- 当前 Host 将设备输入路由到当前主控代理会话；设备不能指定任意 `session_id`。
- 联网与配网由终端自己完成。以太网或其他网络实现也可以接入，协议不要求使用 ESP32 的 Wi-Fi。

建议先实现“文字输入 + 文字输出”终端，验证发现、配对、签名认证、保活与输入确认，再增加音频。
纯文字终端无需 ASR/TTS；声明音频能力时，必须同时检查 Host 实际返回的能力。

## 2. 服务发现与 TLS

### 2.1 mDNS

浏览 `_ez-assistant._tcp.local.`，读取 SRV 中的目标主机与端口，以及 A/AAAA 地址。TXT 字段均为字符串：

| 字段 | 内容 |
|---|---|
| `protocol_major` | `1` |
| `protocol_minor` | `0` |
| `path` | `/device` |
| `installation_id` | 32 个小写十六进制字符，视为 Host 身份标识 |
| `certificate_fingerprint` | 叶证书原始 DER 的 SHA-256，64 个小写十六进制字符，无冒号 |
| `pairing_available` | `true` 或 `false`，表示是否允许首次配对 |

实例显示名可能被 mDNS 自动添加后缀，匹配身份时使用 TXT 的 `installation_id`。
WSS 地址为发现得到的 `wss://<host>:<port>/device`，端口可能变化，不能写死成桌面 HTTP 端口 7240。
当前 ESP32 发现实现使用 IPv4；第三方使用其他地址族前需验证 Host 的实际监听与网络可达性。

未配对时只选择用户明确选择或唯一开放配对的兼容 Host；多个 Host 同时开放时等待用户选择，
不随机绑定。已配对时只选择保存的 `installation_id`，且证书指纹必须匹配保存的 pin。

### 2.2 证书 pin 与 WebSocket

1. 建立 TLS，读取对端叶证书的原始 DER，计算 SHA-256。
2. 首配对时与发现记录的指纹比较，后续连接与持久保存的 pin 比较。
3. **pin 成功前，不发送 HTTP Upgrade、设备 ID、JSON 或音频。** 指纹不匹配立即断开。
4. pin 成功后对 `/device` 执行 RFC 6455 Upgrade，检查 `101`、Upgrade/Connection 和
   `Sec-WebSocket-Accept`，再进入设备握手。

Host 使用自签名证书。若客户端库需要自定义 CA 验证，应使用可在发送应用数据前完成 pin 校验的
TLS 路径；仅设置“不校验证书”不构成安全实现。首次 mDNS 指纹不是认证信任根，后续还必须完成
绑定该指纹的 PAKE 双向确认。

客户端 WebSocket frame 必须 masking；控制消息使用 UTF-8 text message，PCM 使用 binary message。
WebSocket 分片应先重组为消息再解析；一个 PCM message 必须恰好是一帧，不能把多帧粘在一起。
无需额外的自定义 WebSocket subprotocol。处理 WebSocket Ping/Pong/Close；应用层保活另见第 6 节。

## 3. JSON envelope 与通用类型

每条控制消息包含且只包含以下 5 个顶层字段。下例是一个完整消息：

```json
{
  "protocol_major": 1,
  "protocol_minor": 0,
  "message_id": "terminal-message-0001",
  "type": "text_input",
  "payload": {
    "client_input_id": "input-example-0001",
    "text": "你好，请用文字回答。",
    "output_preference": "text"
  }
}
```

| 字段/限制 | 规则 |
|---|---|
| envelope 大小 | UTF-8 编码后最多 65536 bytes |
| `protocol_major/minor` | 无符号 16 位整数；本协议发送 `1/0`。主版本不符拒绝；不同 minor 不代表已完成能力协商 |
| `message_id` | 非空字符串，最多 128 bytes；每次发送使用新 ID，包括重连后的业务重传 |
| `type` | 非空字符串，最多 64 bytes；按本文列出的精确名称发送 |
| `payload` | 按消息类型填写，使用精确字段集合，避免未知字段和重复 JSON key |
| 连接内防重放 | Host 保留最近 256 个接收控制消息 ID；终端仍应保证整个连接内不复用 ID |
| `null` | 表中标注可空的字段显式传 `null`，不要以空字符串代替 |
| 数字 | 使用整数；计数与时间在终端实现中应检查范围，避免浮点截断 |

字符串长度均按 UTF-8 bytes 计算。Host 当前部分可空字段的解码也允许省略，为跨语言一致性，本文
示例统一显式写出 `null`。不要把 `message_id` 当作业务幂等键，业务重试使用 `client_input_id`。

### 3.1 capabilities

能力对象固定包含以下 7 个布尔字段。示例为纯文字终端，可直接作为配对与认证的能力声明：

```json
{
  "input_text": true,
  "input_pcm16_16k_mono": false,
  "output_text": true,
  "output_pcm16_16k_mono": false,
  "playback_cancel": false,
  "display_status": true,
  "display_transcript": true
}
```

| 字段 | 声明终端能够做什么 |
|---|---|
| `input_text` | 提交文字输入 |
| `input_pcm16_16k_mono` | 提交协议规定的 PCM 录音 |
| `output_text` | 接收并展示文字回复 |
| `output_pcm16_16k_mono` | 接收并播放 PCM |
| `playback_cancel` | 请求取消播放 |
| `display_status` | 展示交互状态 |
| `display_transcript` | 展示 ASR 分段转写 |

只声明真实支持的能力。能力参与密码学 transcript，不能改变签名时的字段顺序。PTT、WakeNet、
GPIO、屏幕分辨率、Wi-Fi 配网、OTA 均不是 v1.0 capability。

Host 在 `hello_ack` 中返回有效能力：音频输入与 Host ASR 可用性取交集，音频输出及播放取消与
Host TTS 可用性取交集。后续以有效能力为准。改变终端硬件能力时重新建立连接并认证。

### 3.2 output_preference

取值为 `text`、`audio`、`text_and_audio`，分别要求有效 `output_text`、有效
`output_pcm16_16k_mono` 或两者同时支持。偏好与能力不符会收到 `unsupported_output_preference`。
因此纯音频终端可能已完成配对，却因为 Host 没有 TTS 而无法完成连接握手。

## 4. 首次配对

### 4.1 准备与时序

终端用加密随机源生成并通过自己的可信界面显示 6 位数字码，范围 `000000`～`999999`，保留前导零。
用户在 Desktop 的“添加设备”窗口输入该码。代码不能明文放入设备 wire、普通日志或广告记录。
无屏终端也必须提供一种受控方式让用户取得配对码。

```text
Host → Device  auth_challenge
Device → Host pairing_hello
Host → Device pairing_pending
               等待用户在 Desktop 输入终端上的 6 位码
Host → Device pairing_pake
Device → Host pairing_confirm
Device → Host pairing_bind
Host → Device pairing_bind_ack
               终端原子保存 pending identity
Device → Host pairing_commit
Host → Device pairing_complete
               终端激活身份；Host 关闭配对连接
               重新建立 WSS，执行第 5 节签名认证
```

Host 只在约 5 分钟的配对窗口中接受候选。同一请求最多 5 次确认尝试；终端也应对当前显示码累计
安全失败次数，达到阈值轮换显示码和全部临时量，不能靠重连重置失败计数。

### 4.2 配对消息 payload

下表列出完整字段；所有消息均放在第 3 节 envelope 中。`string` 字段不能为空，具体编码见第 4.3 节。

| `type` | 方向 | `payload` 字段 |
|---|---|---|
| `auth_challenge` | Host → Device | `connection_id:string`、`nonce:string`、`server_time_ms:i64` |
| `pairing_hello` | Device → Host | `pairing_request_id:string`、`display_name:string`、`device_nonce:string`、`capabilities:object`、`pake_share:string` |
| `pairing_pending` | Host → Device | `pairing_request_id:string`、`expires_at_ms:i64` |
| `pairing_pake` | Host → Device | `pairing_request_id:string`、`host_nonce:string`、`pake_share:string`、`confirmation_mac:string` |
| `pairing_confirm` | Device → Host | `pairing_request_id:string`、`confirmation_mac:string` |
| `pairing_bind` | Device → Host | `pairing_request_id:string`、`public_key:string`、`signature:string`、`binding_mac:string` |
| `pairing_bind_ack` | Host → Device | `pairing_request_id:string`、`device_id:string`、`host_proof:string` |
| `pairing_commit` | Device → Host | `pairing_request_id:string`、`device_id:string`、`signature:string`、`binding_mac:string` |
| `pairing_complete` | Host → Device | `pairing_request_id:string`、`device_id:string`、`display_name:string` |

`pairing_request_id` 最多 128 bytes，`display_name` 最多 128 bytes，nonce 最多 256 bytes。
每一步核对同一个 `pairing_request_id`，`device_id` 只能使用 Host 分配的值。
`expires_at_ms`、`server_time_ms` 为 Unix 毫秒时间；不要把它们当作单调时钟值。

### 4.3 密码学与落盘要求

完整算法、双方角色、固定点、transcript、MAC 标签及编码见
[协议密码学附录](协议密码学附录.md)。**只写“SPAKE2 + Ed25519”不足以实现互通，必须逐字节匹配附录和 fixtures。**

- 终端为 SPAKE2 P-256 Party A，Host 为 Party B；使用 SHA-256/HKDF-SHA-256/HMAC-SHA-256。
- 份额为 SEC1 非压缩 P-256 点，解码后 65 bytes。MAC 为 32 bytes，Ed25519 公钥为原始 32 bytes，
  签名为原始 64 bytes；wire 均使用 URL-safe Base64，**不带 `=` padding**。
- PAKE 双向确认完成后才生成长期 Ed25519 身份；长期私钥永不发给 Host。
- 验证 `pairing_bind_ack.host_proof` 后，原子保存 `pending` 身份，再发送 `pairing_commit`。
- Host 验证 commit 并持久登记后返回 `pairing_complete`；终端再激活身份。
- 持久身份至少包含 Host installation ID、证书 pin、Host 分配的 device ID、Ed25519 私钥/seed、
  对应公钥和 pending/active 状态；按终端平台保护存储并防止半写入记录被当作有效身份。

`pairing_complete` 丢失时，保留 pending 身份并先尝试正常认证。认证成功则激活；pending 身份
被明确拒绝后可以清掉该 pending 凭据并重新配对。active 身份认证失败不能自动清除再配对。

同一未过期尝试的短暂断线可以重发同一 `pairing_hello`；确认窗口已关闭、尝试已过期或 Host 已重启时，
销毁旧临时量，使用新 request ID、device nonce、私有 scalar/share。当前 ESP32 的显示码在一次启动
会话内保持，除成功、显式重置或安全阈值触发轮换；显示码保持不代表密码学临时量可以跨尝试复用。

## 5. 已配对认证

Host 在每个新 WSS 连接先发 `auth_challenge`。终端必须等收到挑战后再发第一条配对或认证消息。

```json
{
  "protocol_major": 1,
  "protocol_minor": 0,
  "message_id": "host-challenge-example",
  "type": "auth_challenge",
  "payload": {
    "connection_id": "connection-example",
    "nonce": "host-nonce-example",
    "server_time_ms": 1792454400000
  }
}
```

已配对终端用新生成的 `device_nonce` 构造认证 transcript，并用保存的 Ed25519 私钥签名。发送
`hello` 的 payload：

| 字段 | 规则 |
|---|---|
| `device_id` | Host 之前分配的 opaque string，最多 256 bytes |
| `device_nonce` | 新随机 nonce；建议 32 随机 bytes 的 Base64url，无 padding，最多 256 bytes |
| `capabilities` | 本次声明的完整能力对象 |
| `output_preference` | 三种偏好之一，参与签名 |
| `client_version` | 非空终端版本，最多 128 bytes，例如 `vendor-terminal/1.0.0` |
| `signature` | 附录中 `auth_transcript` 的 Ed25519 签名，Base64url 编码 |

Host 返回 `hello_ack`：

```json
{
  "protocol_major": 1,
  "protocol_minor": 0,
  "message_id": "host-ack-example",
  "type": "hello_ack",
  "payload": {
    "device_id": "device-example",
    "connection_id": "connection-example",
    "capabilities": {
      "input_text": true,
      "input_pcm16_16k_mono": false,
      "output_text": true,
      "output_pcm16_16k_mono": false,
      "playback_cancel": false,
      "display_status": true,
      "display_transcript": true
    },
    "output_preference": "text"
  }
}
```

终端核对 device ID 与 challenge 的 connection ID，并采用返回的有效能力。只有收到并验证
`hello_ack` 后才认为已在线并发送业务消息。当前 Host 的普通握手步骤超时为 30 秒；配对等待用户确认
使用配对窗口截止时间。`auth_challenge.nonce` 与 `pairing_pake.host_nonce` 是不同用途的随机值。

## 6. 保活、偏好与文字交互

本节示例均为 **payload**，发送时必须补完整 envelope 和新的 `message_id`。

### 6.1 应用层 ping/pong

Host 约每 15 秒发送 `type=ping`，payload 为：

```json
{"nonce":"heartbeat-example","sent_at_ms":1792454400000}
```

终端尽快回复 `type=pong`，**原样返回该 payload**，使用新的 envelope message ID。
这不是 WebSocket opcode Ping/Pong。Host 当前在保活检查时若超过 25 秒未收到活动会关闭连接；
不能依赖媒体流量或仅处理 WebSocket Ping 来替代应用层 pong。终端也应设置有界接收超时并重连。

### 6.2 输出偏好

终端可发送 `set_output_preference`，Host 成功后返回 `output_preference_changed`，两者 payload 均为：

```json
{"output_preference":"text"}
```

只对当前连接及后续按预设投递的输出生效，不能改变已经冻结到某一输入轮次的偏好。

### 6.3 文字输入与确认

`text_input` 的 payload：

```json
{"client_input_id":"text-example-0001","text":"你好，请用一句话回答。","output_preference":"text"}
```

`client_input_id` 非空，最多 256 bytes；`text` 非空，最多 49152 bytes。
Host 使用当前主控会话提交成功后返回 `input_accepted`：

```json
{"client_input_id":"text-example-0001","input_id":"input-example","run_id":"run-example","queue_state":"accepted"}
```

`queue_state` 使用当前 Run 状态：`accepted`、`running`、`cancelling`、`completed`、`failed`、
`cancelled`、`interrupted`、`compaction_required`。它是接纳时的状态快照，不保证以后还会推送完整 Run 生命周期。
`input_accepted` 不表示 Agent 已回答。

有文字输出时，Host 发送 `text_output`：

```json
{"output_id":"output-example","run_id":"run-example","text":"你好。"}
```

不要假定输出只属于最近一次本地输入；按 `run_id`、`output_id` 关联。设备可能也是托管输出目标。

## 7. 上行音频与输入聚合

### 7.1 固定音频格式

`format` 对象必须精确为：

```json
{"encoding":"pcm_s16le","sample_rate_hz":16000,"channels":1,"frame_duration_ms":20}
```

每帧 320 个有符号 16 位小端样本，即 640 bytes。输入不带 WAV/MP3/Opus 文件头。
采样率、声道或编码不匹配时，第三方终端先在本地转换。

### 7.2 listen_start → PCM → listen_stop

1. 用户开始本段录音时，终端发送 `listen_start`：

```json
{"client_input_id":"speech-segment-example-0001","stream_id":42,"format":{"encoding":"pcm_s16le","sample_rate_hz":16000,"channels":1,"frame_duration_ms":20},"output_preference":"audio"}
```

2. 使用同一个非零 `stream_id:u32` 发送二进制 PCM，sequence 从 **0** 开始，逐帧加 1。
3. 最后一帧不足 320 样本时补零，仍发送固定长度帧。上行协议不单独携带末帧有效样本数。
4. 结束后发送 `listen_stop`，`last_sequence` 为最后一帧的序号，**不是帧数**：

```json
{"stream_id":42,"last_sequence":9}
```

这表示已经发送 10 帧音频。只发送一帧时 `last_sequence=0`。没有音频时可以发送 `listen_cancel`；
当前 Host 也会将零帧 `listen_stop` 作为空输入处理，返回 idle/no_speech_recognized，不创建 Run。

取消本段发送 `listen_cancel`：

```json
{"stream_id":42}
```

同一连接同时最多接收一段上行流；每段 PCM 上限为 1920000 bytes，即 60 秒或 3000 帧。
`listen_start` 无单独 start ACK；Host 可异步返回错误，终端必须同时处理下行控制消息。

### 7.3 两级接管确认

Host 校验 `listen_stop` 与帧序列后返回 `input_segment_accepted`：

```json
{"client_input_id":"speech-segment-example-0001","stream_id":42}
```

收到它，表示 Host 已接管这一段 PCM，终端可以释放该段的重传缓存。**它不表示 ASR 成功，也不表示
Runtime 已创建输入或 Run。**

Host 可异步发送 `transcript`，仅当有效能力包含 `display_transcript=true`：

```json
{"client_input_id":"speech-segment-example-0001","text":"请介绍一下这个设备。"}
```

当前 Host 在段结束后等待约 2 秒聚合窗口，并等待本轮已接管段的 ASR 完成；窗口内新的
`listen_start` 会暂停收口，后续段结束后重启收口计时。同一逻辑轮最多 16 段，输出偏好保持一致。
每段使用自己的 `client_input_id`；整轮使用第一段 ID 作为逻辑输入 ID，按段顺序合并识别文字，
然后只提交一次 Runtime，最终返回第 6 节的 `input_accepted`。

不要因为短暂没有 `input_accepted` 就再次提交一份新 ID 的输入。若无有效识别文字，Host 返回
idle 状态，不一定创建 Run。整句识别与合成不保证实时逐字转写或 Provider 首包流式返回。

## 8. PCM 二进制帧

每个 WebSocket binary message **固定 656 bytes**，前 16 bytes 是网络字节序头，之后 640 bytes
是小端 PCM。不要将头字段也写成小端。

| offset | 长度 | 字段 | 规则 |
|---:|---:|---|---|
| 0 | 1 | `version:u8` | 固定 `1` |
| 1 | 1 | `direction:u8` | 上行 `1`，下行 `2` |
| 2 | 2 | `flags:u16be` | 固定 `0` |
| 4 | 4 | `stream_id:u32be` | 与 start 对应，非零 |
| 8 | 4 | `sequence:u32be` | 每条流从 `0` 开始逐帧递增，不跳号、不重复 |
| 12 | 2 | `payload_len:u16be` | 固定 `640`，即 `0x0280` |
| 14 | 2 | `reserved:u16be` | 固定 `0` |
| 16 | 640 | PCM | 320 个 int16 little-endian 样本 |

fixtures 中 `stream_id=42`、`sequence=7` 的上行头为
`010100000000002a0000000702800000`，下行头为
`010200000000002a0000000702800000`。这只是头部测试向量，不表示新流从序号 7 开始。

WebSocket 本身有序，当前协议不定义逐帧 ACK、缺帧补包或基于 sequence 的网络重排。
非法长度、版本、方向、保留位、stream ID 或序号应停止本流并报告/断开，不能静默纠正。

## 9. 下行播报、排空与取消

Host 先发送 `playback_start`：

```json
{"output_id":"output-audio-example","run_id":"run-example","stream_id":73,"format":{"encoding":"pcm_s16le","sample_rate_hz":16000,"channels":1,"frame_duration_ms":20},"text":"你好，这是语音回复。","sample_count":350}
```

随后发送 `direction=2` 的二进制帧，sequence 从 0 开始。上例有效样本数为 350，需要 2 帧；
末帧仅前 30 个样本有效，其余补零。**按 `sample_count` 截取实际播放长度**，不要把补零尾部当成额外语音。

Host 发完一段后发送 `playback_end`：

```json
{"output_id":"output-audio-example","stream_id":73,"reason":"completed"}
```

当前可能出现的 reason 包括 `completed`、`cancelled`、`interrupted_by_input`、`replaced`、
`revoked`、`shutdown`、`backpressure`。终端应保守处理未知结束原因：停止该段，不把它认作正常完成。

- `completed` 只表示 Host 已发送完该段。终端仍要等待自己的 PCM/I2S/系统播放器缓冲排空，再显示
  本地播放完成；协议没有“扬声器物理完成 ACK”。
- Host 连续发送的多个播报段必须在终端按 FIFO 播放。下一段到达不等于上一段的本地缓冲已经排空。
- 对正常完成同时核对有效样本数、序号和结束消息；断线、close 或缓冲暂空均不能代替正常结束。
- 预缓冲、欠载恢复和本地音量由终端实现。Host 当前按约 20 ms 发送一帧，终端需有界缓冲并持续读消息。
- 对过期连接、已取消流及迟到帧丢弃，不允许旧播报在新输入后复活。

终端主动取消播放时，若声明了有效 `playback_cancel`，发送：

```json
{"output_id":"output-audio-example","stream_id":73}
```

当前 Host 仅在它匹配队首活动播放时接受，并取消当前及排队播放；不匹配返回 `playback_not_active`。
终端还应立即停止自己的播放器并清理受影响的本地队列；Host 可能已经发送完音频，不能依靠远端取消
来停止仍留在本地缓冲中的声音。
该消息停止播放，**不等于取消 Runtime 的 Agent Run**。新的 `listen_start` 会抢占旧播报，Host 再依据
输入是否仍在聚合或已提交 Runtime 处理同轮补充/活动 Run 取消。

## 10. 交互状态与错误

### 10.1 state_changed

Host 可发送状态投影：

```json
{"run_id":null,"client_input_id":"speech-segment-example-0001","state":"recognizing","reason":null}
```

完整字段为 `run_id:string|null`、`client_input_id:string|null`、`state:string`、`reason:string|null`。
当前 Host 路径会发送 `listening`、`recognizing`、`idle`、`unavailable` 等状态；reason 可能为
`no_speech_recognized`、`cancelled`、`tts_provider_failed`、`no_speak_text` 或输入拒绝短码。
不要要求每轮一定收到 listening → recognizing → speaking → idle 的固定完整序列；终端应结合
自身输入动作、输入确认、播放流和错误投影界面，不把 `state_changed` 作为 Run 权威状态。

### 10.2 error

```json
{"code":"unsupported_output_preference","correlation_message_id":"terminal-hello-example","recoverable":true}
```

`correlation_message_id` 可以为 `null`。`recoverable` 指该错误是否允许受控恢复，不保证请求成功，
也不表示 Host 一定保持连接。处理错误后还要处理 Close。部分异常会直接关闭连接而没有 error 消息。

| 错误/类型 | 典型处理 |
|---|---|
| `pairing_not_open`、`pairing_failed` | 等用户开放配对或重新确认，受控重试并保留失败计数 |
| `authentication_required`、`authentication_failed` | 停止业务发送；active 身份阻断并提示，pending 身份按第 4 节恢复 |
| `unsupported_output_preference` | 核对偏好及 Host TTS/文字能力，不清除配对 |
| `unsupported_input_capability`、`unsupported_message`、`unsupported_playback_cancel` | 修正终端能力与所发消息 |
| `invalid_text_input`、`invalid_listen_start`、`invalid_listen_stop` | 核对字段、格式和流状态，不能盲目补发音频 |
| `asr_unavailable`、`asr_auth_failed`、`asr_timeout`、`asr_provider_failed`、`asr_empty_transcript` | 结束/恢复当前输入，提示 Host 配置或 Provider 问题，不重新配对 |
| `audio_input_busy`、`voice_turn_limit_reached`、`voice_turn_too_large` | 控制同时录音数、聚合段数和输入大小 |
| `audio_stream_not_active`、`pcm_without_active_stream`、`playback_not_active` | 当前流已结束或 ID 不符，核对本地状态 |
| `invalid_pcm_frame`、`invalid_pcm_sequence`、`pcm_stream_mismatch`、`audio_input_too_large` | 非法音频流，Host 通常返回不可恢复错误并断开 |
| `client_input_reused` | 同 ID 对应了不同内容或偏好，禁止自动改 ID 重放已提交操作 |
| `controller_unavailable`、`runtime_unavailable`、`input_rejected` | 提示用户处理当前主控会话或 Runtime 状态 |
| `connection_replaced` | 同设备新认证连接替换本连接，停止旧连接发送，避免双方持续抢占 |
| `gateway_disabled` | 等待用户重新开启设备接入，保留身份 |
| `device_revoked` 且不可恢复 | 仅在已 pin 的可信 Host 上接受撤销，清除设备凭据并回到配对 |

表中是当前实现的主要短码，不是一个可据此忽略未知码的封闭枚举；冻结 envelope fixture 中还有
历史错误码。未知错误应安全结束受影响操作，按 recoverable 与连接状态决定是否退避，不自动删除身份。

## 11. 断线、重传与幂等边界

每次 WSS 重连重新验证证书并执行 challenge/hello，不跨连接复用签名、nonce、message ID 或活动流 ID。
建议为本地连接分配 epoch，使旧连接回调与迟到 PCM 无法污染新连接。

| 断线时进度 | 恢复规则 |
|---|---|
| 音频尚未收到 `input_segment_accepted` | 保留完整 PCM；重连后用同一 `client_input_id` 和冻结偏好、新流 ID，从 sequence 0 完整重发 |
| 已收到 `input_segment_accepted`，尚无 `input_accepted` | 可以释放 PCM；等待 Host 现存聚合/识别结果，不能自动新建一轮相同输入 |
| 已收到 `input_accepted` | 不再次提交；不假定重连会回放历史输出 |
| 下行播放过程中断线 | 停止播放并清理旧连接队列；不自动播放旧回复 |
| Host 进程重启 | 稳定配对记录可保留，但在内存中的 PCM、ASR、聚合和媒体进度没有持久恢复保证 |

重传同 ID 的内容和输出偏好必须一致。Host 当前连接内保留最多 1024 个输入指纹；同进程中未收口的
语音聚合可按设备跨 WSS 保留，但它是有界易失状态。Runtime 使用稳定客户端输入标识参与业务去重；
**不能把这些机制外推为所有音频、所有重启场景的端到端 exactly-once 保证。**

文字输入需要重试时也保持原 `client_input_id`、原文与偏好。收到已提交确认后不能再自动发送；
遇到“是否已执行”不确定且操作可能有副作用时，交给用户核对，不通过更换 ID 强制重做。

网络或服务暂时不可用时使用有上限并带抖动的退避；当前 ESP32 瞬态连接退避基值为
1/2/4/8/15 秒，发现服务不可用为 2/4/8/10 秒。它们是参考终端策略，不是第三方必须照搬的 wire 字段。
证书变化、active 身份认证失败和冲突应进入可见阻断状态，不能作为一般网络错误无限重试。

## 12. 第三方实现验收清单

1. **离线字节校验**：通过 `crypto-v1.json` 的份额、确认 MAC、session key、transcript、Ed25519
   公钥与签名向量；通过 `pcm-v1.json` 和 `envelope-v1.json`，拒绝负例。
2. **纯文字链路**：独立设备身份，发现目标 Host、人工确认配对、保存 pending/active、重启后认证、
   应用层 pong、提交文字、收到 input_accepted 和 text_output。
3. **能力协商**：验证纯文字、纯音频、混合终端；ASR/TTS 缺失时只使用有效能力，并正确显示拒绝原因。
4. **音频链路**：首帧 sequence 0、末帧补零、last_sequence、60 秒限制、分段确认、聚合与转写、
   多段播报 FIFO、sample_count、正常排空与取消。
5. **故障恢复**：断线前后两级确认、Host 重启、网关关闭/开启、证书不匹配、active 认证失败、
   在线/离线撤销、重复连接、旧帧丢弃、缺帧/重复帧和消息重放。
6. **实录实听**：使用真实 Provider 验证识别结果、音量、完整播放与抢占；本地 ready、队列接纳或
   Host 发送完成均不能单独作为物理播放成功的证明。

本仓的 `firmware/test/run_host_tests.sh` 可作为 C 实现的离线回归入口；上游 Node 参考终端及其
crypto/PCM/state 测试、M5～M8 联调脚本可作为独立对照。测试中的固定 seed、scalar、nonce 和配对码
只属于 fixtures，不能用于真实设备身份。

第三方接入无需修改 Host 才能使用已经声明的能力；若需要新编码、消息、capability 或任意会话路由，
先按联合版本流程演进协议，不在 v1.0 上私自添加字段并声称兼容。
